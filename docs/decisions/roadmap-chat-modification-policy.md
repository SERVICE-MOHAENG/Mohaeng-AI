# 요약

로드맵 채팅 수정 기능은 사용자가 자연어로 로드맵을 쉽게 조작할 수 있어야 하므로, 기존 장소 단위 수정 중심 정책을 일차 단위 재배치까지 확장합니다.
단기 목표는 `같은 일차 내 장소 수정`에 더해 `일차 간 장소 이동`과 `일차 일정 묶음 교체`를 지원하는 것입니다.
NestJS와 Mohaeng-AI 사이의 callback 계약은 최종 로드맵 전체 스냅샷을 전달하는 구조이므로, 이 정책 확장을 위해 BE 저장 로직이나 통신 payload를 변경할 필요는 없습니다.

# 배경

로드맵 수정 기능은 모행 서비스의 핵심 사용자 경험입니다.
사용자는 JSON 구조를 직접 편집하지 않고도 "1일차랑 2일차 일정을 바꿔줘", "2일차 첫 번째 장소를 1일차 마지막으로 옮겨줘" 같은 자연어로 로드맵을 조작하기를 기대합니다.

현재 명세와 구현은 장소 교체, 추가, 삭제, 같은 일자 내 순서 이동에 집중되어 있습니다.
이 정책은 데이터 무결성 측면에서는 안전하지만, 사용자가 기대하는 일정 재배치 경험을 정책상 거부하게 되어 제품 핵심 가치와 충돌합니다.

BE 쪽 저장 흐름은 `SUCCESS` callback의 `modified_itinerary` 전체 스냅샷을 받아 기존 `CourseDay`와 `CoursePlace`를 재구성하는 방식입니다.
따라서 Mohaeng-AI가 일관된 최종 로드맵 스냅샷을 내려주면, BE는 일차 간 이동이나 일차 일정 교체를 별도 patch 로직 없이 저장할 수 있습니다.

# 본문

## 결정

로드맵 채팅 수정 정책을 다음 3단계로 구분합니다.

| 단계 | 정책 | 처리 방향 |
| --- | --- | --- |
| 1단계 | 같은 일차 내 장소 수정 | 즉시 지원 |
| 2단계 | 일차 간 장소 이동과 일차 일정 묶음 교체 | 지원 대상으로 확장 |
| 3단계 | 여행 날짜, 기간, 숙박 수 변경 | 수정이 아니라 재구성 또는 재생성 제안으로 분리 |

이번 결정의 적용 범위는 2단계까지입니다.
3단계는 기존 로드맵의 구조 자체를 바꾸는 작업이므로, 일반 채팅 수정과 분리된 재구성 플로우로 다룹니다.

## 지원할 수정 유형

### 같은 일차 내 장소 수정

기존 정책을 유지합니다.

| 사용자 의도 | Operation | 결과 |
| --- | --- | --- |
| 특정 장소를 다른 장소로 교체 | `REPLACE` | 대상 장소를 Google Places 기반 새 장소로 교체 |
| 특정 위치에 장소 추가 | `ADD` | 대상 일차의 지정 위치에 장소 삽입 |
| 특정 장소 삭제 | `REMOVE` | 대상 장소 삭제 |
| 같은 일차 안에서 순서 변경 | `MOVE` | 대상 일차 내부의 `visit_sequence` 재정렬 |

### 일차 간 장소 이동

새로 지원합니다.

예시:

- "2일차 첫 번째 장소를 1일차 마지막으로 옮겨줘"
- "3일차 카페를 2일차 점심 뒤로 옮겨줘"
- "마지막 날 첫 장소를 첫날 끝으로 보내줘"

처리 규칙:

- 출발 일차와 도착 일차가 달라도 `MOVE`로 처리합니다.
- 출발 일차는 이동 후에도 최소 1개 장소를 유지해야 합니다.
- 도착 일차는 이동 후에도 최대 10개 장소를 넘지 않아야 합니다.
- 출발 일차와 도착 일차의 `visit_sequence`를 모두 1부터 재정렬합니다.
- 출발 일차와 도착 일차의 `visit_time`을 모두 재계산합니다.
- `diff_keys`는 영향을 받은 양쪽 일차의 변경 위치를 포함합니다.

### 일차 일정 묶음 교체

새로 지원합니다.

예시:

- "1일차랑 2일차 일정 바꿔줘"
- "첫날 코스와 마지막 날 코스를 서로 바꿔줘"

처리 규칙:

- 날짜 자체를 바꾸는 것이 아니라, 각 날짜에 배치된 `places` 묶음을 서로 교체합니다.
- `day_number`와 `daily_date`는 기존 일차의 값을 유지합니다.
- 교체된 각 일차의 장소 목록은 해당 일차 안에서 `visit_sequence`를 1부터 재정렬합니다.
- 교체된 두 일차 모두 `visit_time`을 재계산합니다.
- `diff_keys`는 교체된 양쪽 일차의 장소 카드를 하이라이트할 수 있도록 생성합니다.

## 계속 제한할 수정 유형

다음 요청은 일반 수정으로 처리하지 않습니다.

| 사용자 의도 | 처리 |
| --- | --- |
| 여행 시작일 또는 종료일 변경 | 재구성 또는 재생성 제안 |
| 2박 3일을 3박 4일로 변경 | 재구성 또는 재생성 제안 |
| 일차 자체 삭제 | 재구성 또는 재생성 제안 |
| 빈 일차 추가 | 재구성 또는 재생성 제안 |
| 지역 자체 변경 | 재생성 제안 |

이 유형은 `REJECTED`로 단순 거부하기보다, 가능한 경우 `ASK_CLARIFICATION` 또는 별도 재생성 플로우로 연결하는 사용자 경험을 지향합니다.
단, 별도 재생성 플로우가 구현되기 전에는 기존처럼 명확한 안내 메시지를 반환합니다.

## 통신 계약

Mohaeng-AI와 NestJS 사이의 callback 계약은 변경하지 않습니다.

`SUCCESS` callback은 항상 수정 완료된 전체 로드맵 스냅샷을 `modified_itinerary`로 전달합니다.
NestJS는 현재 구조대로 기존 `CourseDay`와 `CoursePlace`를 삭제한 뒤 callback payload 기준으로 다시 생성할 수 있습니다.

필수 payload 조건은 다음과 같습니다.

| 필드 | 조건 |
| --- | --- |
| `modified_itinerary.start_date` | 기존 여행 시작일 유지 |
| `modified_itinerary.end_date` | 기존 여행 종료일 유지 |
| `modified_itinerary.trip_days` | 기존 여행 일수 유지 |
| `modified_itinerary.nights` | 기존 숙박 수 유지 |
| `itinerary[].day_number` | 기존 일차 번호 유지 |
| `itinerary[].daily_date` | 기존 일차 날짜 유지 |
| `places[].place_id` | 빈 값 금지 |
| `places[].visit_sequence` | 일차별 1부터 순차 정렬 |
| `places[].visit_time` | 수정 후 일차 기준으로 재계산 |

`GENERAL_CHAT`, `ASK_CLARIFICATION`, `REJECTED`, `FAILED` 상태에서는 기존 정책처럼 `modified_itinerary`를 포함하지 않거나 `null`로 둡니다.

## Mohaeng-AI 구현 영향

정책 확장은 주로 Mohaeng-AI 내부 그래프에 반영합니다.

| 영역 | 변경 방향 |
| --- | --- |
| `analyze_intent` | 일차 간 장소 이동과 일차 일정 묶음 교체를 정책상 거부하지 않도록 의도 분류 확장 |
| `ChatIntent` | 필요하면 일차 묶음 교체를 표현할 operation 또는 보조 필드 추가 |
| `mutate` | 일차 간 `MOVE`와 day places swap을 실제 수정으로 처리 |
| `propose_visit_time` | 영향을 받은 모든 일차를 visit time proposal 대상으로 포함 |
| `cascade` | 영향을 받은 모든 일차에 visit time policy 적용 및 스키마 검증 |
| `respond` | 일차 간 이동과 일차 교체 결과를 사용자에게 명확히 설명 |
| `diff_keys` | 단일 장소뿐 아니라 양쪽 일차의 변경 범위를 표현 |

### Intent 표현 결정

일차 일정 묶음 교체를 위해 새로운 intent 모델이나 새 `ChatOperation`을 만들지는 않습니다.
기존 `ChatIntent` 구조와 `ChatOperation` 중심 흐름을 유지하되, `ChatIntent` 내부에 보조 scope 필드를 두어 장소 단위 교체와 일차 일정 묶음 교체를 구분합니다.
이 필드는 Mohaeng-AI 내부 그래프 상태에서만 사용하며, BE callback 계약에는 포함하지 않습니다.

권장 표현은 다음과 같습니다.

| 의도 | `op` | 보조 scope | 필수 필드 | 해석 |
| --- | --- | --- | --- | --- |
| 장소 단위 교체 | `REPLACE` | `ITEM` | `target_day`, `target_index`, `search_keyword` | 대상 장소를 Google Places 기반 새 장소로 교체 |
| 일차 일정 묶음 교체 | `REPLACE` | `DAY_PLACES` | `target_day`, `destination_day` | 두 일차의 `places` 묶음을 서로 교체 |

보조 scope 필드명은 구현 시 `target_scope` 또는 `replace_scope` 중 하나로 정하되, 기존 classifier의 `DAY_LEVEL` 의미와 혼동되지 않도록 `DAY_PLACES` 값을 사용합니다.
`DAY_LEVEL`은 날짜, 기간, 일차 삭제처럼 로드맵 구조를 바꾸는 요청을 뜻하고, `DAY_PLACES`는 날짜를 유지한 채 해당 일차에 배치된 장소 묶음만 바꾸는 요청을 뜻합니다.

### diff_keys 표현 결정

`diff_keys`는 기존 장소 카드 단위 형식을 유지합니다.
즉, 일차 간 수정이 발생해도 `day1_place1`, `day2_place1` 같은 기존 형식의 키 목록으로 표현합니다.
day 단위 하이라이트를 위한 별도 key는 추가하지 않습니다.

일차 일정 묶음 교체처럼 한 번에 여러 일차가 바뀌는 경우에는 영향을 받은 각 일차의 장소 카드 key를 모두 포함합니다.
프론트엔드는 특정 day에 속한 `diff_keys`가 하나 이상 존재하면 해당 day 전체를 보조 하이라이트할 수 있습니다.
이는 FE 표시 정책이며, Mohaeng-AI와 BE 사이의 통신 계약에는 포함하지 않습니다.

### 일차 간 장소 이동 해석 규칙

일차 간 장소 이동은 AI 내부 intent 분석과 mutation에서만 처리하며, callback payload 계약은 변경하지 않습니다.
자연어 위치 표현은 다음 휴리스틱을 적용합니다.

| 사용자 표현 | 내부 해석 |
| --- | --- |
| "1일차 마지막으로" | 도착 일차의 `len(places) + 1` 위치에 삽입 |
| "1일차 처음으로" | 도착 일차의 `1` 위치에 삽입 |
| "점심 뒤로", "카페 다음으로" | 해당 장소 또는 시간대 anchor의 다음 `visit_sequence`로 삽입 |
| "점심 앞으로", "카페 전에" | 해당 장소 또는 시간대 anchor의 현재 `visit_sequence`로 삽입 |

anchor가 여러 개라 대상을 특정할 수 없으면 `ASK_CLARIFICATION`으로 처리합니다.

### 일차 일정 묶음 교체 불변 조건

일차 일정 묶음 교체는 날짜 자체를 바꾸는 작업이 아닙니다.
따라서 mutation은 각 day 객체의 `day_number`, `daily_date`, 기타 day-level 메타데이터를 유지하고 `places` 배열만 서로 교체해야 합니다.
교체 후 각 day의 `visit_sequence`는 1부터 다시 정렬하고, `visit_time`은 해당 일차 기준으로 다시 계산합니다.

### 다중 일차 재계산

수정 기능은 이제 한 번의 요청으로 여러 일차에 영향을 줄 수 있습니다.
따라서 `propose_visit_time`과 `cascade`는 단일 day가 아니라 영향받은 day 집합을 batch로 처리해야 합니다.
영향받은 일차는 `diff_keys`에서 추출하되, 일차 일정 묶음 교체와 일차 간 장소 이동에서는 출발 일차와 도착 일차를 모두 포함해야 합니다.

향후 "여러 날 일정을 한 칸씩 밀어줘"처럼 7개 이상의 일차가 한 번에 바뀌는 요청까지 고려해, visit time 제안과 policy 적용은 day 목록 기반 batch 처리 구조를 유지합니다.
단, 여행 기간과 숙박 수를 바꾸는 요청은 여전히 일반 수정이 아니라 재구성 또는 재생성 플로우로 분리합니다.

## BE 구현 영향

현재 확인한 BE 구조에서는 필수 변경이 없습니다.

BE는 `IntentStatusType`이 `SUCCESS`이고 `modifiedItinerary`가 존재하면 `TravelCourse`를 전체 스냅샷 기준으로 재작성합니다.
따라서 Mohaeng-AI가 위 payload 조건을 지키면, 일차 간 장소 이동과 일차 일정 묶음 교체를 기존 callback 구조로 저장할 수 있습니다.

다만 BE 관점의 주의사항은 다음과 같습니다.

- `place_id`가 비어 있으면 해당 장소가 저장되지 않으므로 Mohaeng-AI는 기존 장소 이동 시 원래 `place_id`를 보존해야 합니다.
- `daily_date`가 변경되면 사용자 의도와 다른 날짜 변경으로 해석될 수 있으므로, 일차 묶음 교체에서는 날짜를 유지해야 합니다.
- `diff_keys`는 저장 기준이 아니라 프론트엔드 하이라이트와 대화 기록용 메타데이터로 유지합니다.

## 사용자 경험 기준

정책 메시지는 "지원하지 않습니다"보다 "어떤 방식으로 처리되는지"를 우선 설명해야 합니다.

예를 들어 "1일차랑 2일차 바꿔줘"는 날짜 변경 요청이 아니라 일정 묶음 교체로 해석합니다.
사용자에게는 "1일차와 2일차에 배치된 장소 일정을 서로 바꿨어요. 여행 날짜 자체는 유지했어요."처럼 결과를 설명합니다.

"여행 날짜를 내일로 바꿔줘"처럼 여행 기간 자체가 바뀌는 요청은 일반 수정으로 처리하지 않습니다.
사용자에게는 전체 일정 재구성이 필요하다는 점과 기존 장소를 유지해 재구성할 수 있다는 점을 안내합니다.

## 결과

이 결정으로 로드맵 수정 기능은 단순 장소 편집을 넘어 사용자가 기대하는 일정 재배치 경험을 제공할 수 있습니다.
동시에 여행 날짜, 기간, 숙박 수처럼 전체 구조를 바꾸는 요청은 별도 재구성 플로우로 분리해 데이터 무결성을 유지합니다.

통신 계약과 BE 저장 구조를 유지하므로, 변경 범위는 Mohaeng-AI의 의도 분석, mutation, visit time 재계산, 응답 메시지 정책에 집중됩니다.
