# 요약

이 문서는 Mohaeng-AI 프로젝트의 커밋 메시지 작성 규칙을 정의합니다.
커밋 메시지는 작업 분류, Gitmoji, 변경 요약, 선택적 이슈 번호를 포함해 코드 이력을 빠르게 이해할 수 있도록 작성합니다.

# 배경

커밋 메시지 형식이 일관되지 않으면 변경 이력을 추적하거나 릴리즈 노트를 정리하기 어렵습니다.
작업 유형과 변경 의도를 헤더에 명확히 남기면 리뷰어와 이후 작업자가 변경 맥락을 빠르게 파악할 수 있습니다.

# 본문

## 커밋 메시지 구조

커밋 메시지는 헤더를 필수로 작성하고, 필요한 경우 본문을 추가합니다.
관련 이슈가 있을 때는 헤더 끝에 이슈 번호를 괄호로 명시합니다.

```text
<type> <gitmoji>: <subject> (#issue-number)

<body>
```

본문은 선택 사항입니다.
본문을 작성할 때는 헤더와 본문 사이에 빈 줄을 하나 둡니다.

## 작업 분류

| Type | Gitmoji | 설명 |
| --- | --- | --- |
| `feat` | ✨ | 새로운 기능 추가 |
| `fix` | 🐛 | 버그 수정 |
| `docs` | 📝 | 문서 수정 |
| `style` | 💄 | 코드 의미에 영향을 주지 않는 변경 |
| `refactor` | ♻️ | 코드 리팩토링 |
| `test` | ✅ | 테스트 코드 추가 및 수정 |
| `chore` | 🔧 | 빌드, 패키지 설정, 초기 세팅 등 기타 작업 |
| `design` | 🎨 | UI/UX 디자인 변경 |
| `rename` | 🚚 | 파일 또는 폴더명 수정 및 이동 |
| `remove` | 🔥 | 파일 삭제 |

## 헤더 작성 규칙

- 형식은 `<type> <gitmoji>: <subject> (#issue-number)`를 사용합니다.
- 제목 끝에는 마침표를 붙이지 않습니다.
- 영문으로 작성할 때는 과거형보다 명령형 또는 현재형을 사용합니다.
- 이슈 번호가 있을 때는 제목 뒤에 한 칸을 띄우고 `(#번호)` 형태로 작성합니다.
- 이슈 번호가 없으면 괄호를 생략합니다.

## 본문 작성 규칙

본문은 변경 내용의 맥락이 헤더만으로 충분하지 않을 때 작성합니다.
무엇을 바꿨는지뿐 아니라 왜 바꿨는지를 함께 적습니다.

본문에는 다음 내용을 포함할 수 있습니다.

- 변경 이유
- 주요 구현 방식
- 의도적으로 제외한 범위
- 후속 작업 또는 주의 사항

## 예시

이슈 번호가 있는 커밋:

```text
feat ✨: 카카오 로그인 API 연동 (#12)
```

```text
fix 🐛: 로그인 시 토큰 만료 에러 수정 (#45)
```

이슈 번호가 없는 커밋:

```text
chore 🔧: initial project setup
```

```text
docs 📝: README.md 요구사항 업데이트
```

본문을 포함하는 커밋:

```text
refactor ♻️: API 호출 로직 공통 컴포넌트화 (#8)

- 중복되는 fetch 로직을 별도 훅으로 분리
- 에러 핸들링 로직 추가
```
